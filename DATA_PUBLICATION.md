# Publishing the data of this repository

No data file is published through the git repository. The measurements are on PANGAEA, every other
input file is in one Zenodo data record (one file per data set), and everything else is regenerated by
`pixi run all`. The code repository keeps code, `expected_numbers.txt`, the table bodies and
`data/manifest.tsv`, which lists every data file with its size, SHA-256 checksum and archive;
`pixi run data-manifest` checks the local files against it, `pixi run data-manifest --write` recomputes it.

## 1. What goes where

**A. PANGAEA, already published** (archive `pangaea:published`; downloaded by `pixi run fetch-pangaea`,
`scripts/fetch_pangaea.py`, with size and checksum check). The bundle *Observations from the BACSAM II
aircraft campaign with Polar 6* ([doi:10.1594/PANGAEA.995979](https://doi.org/10.1594/PANGAEA.995979),
CC BY 4.0): the 100 Hz T-Bird observations ([995975](https://doi.org/10.1594/PANGAEA.995975)), the 100 Hz
Polar 6 nose boom ([995974](https://doi.org/10.1594/PANGAEA.995974)) and the 50 Hz KT-19 temperature
([995980](https://doi.org/10.1594/PANGAEA.995980)) into `data/pangaea/<dataset>/`, which `pixi run inputs`
cuts to the legs; and the 13 Polar 6 master tracks ([971763](https://doi.org/10.1594/PANGAEA.971763), one
dataset per flight, PANGAEA text export, byte-identical to the files the figures were made with) into
`data/observations/raw/polar6/mastertracks/` (Fig. 1).

**B. Zenodo data record** (archive `zenodo:data`, 22 files, about 197 MB; downloaded by
`pixi run fetch-zenodo`, `scripts/fetch_zenodo.py`, which maps the record's file names to the paths of the
repository and checks them against the manifest): the ERA5 model-level and single-level subsets and the
three CARRA files (`data/reanalysis/`), the MODIS/Aqua ice surface temperature
(`preprocessing/build_modis_ist.py`) and the merged MODIS–AMSR2 sea-ice concentration
(`data/observations/processed/satellite_unified/`), the 13 NASA GIBS images behind Fig. 5
(`figures_manuscript/_gibs_cache/`), and the leg table `data/observations/ar/analysis_ready_polar6_legs_metadata.csv`
(start and end of every straight leg, cut once from the Polar 6 archive by `preprocessing/flight_segments.py`).

**C. Regenerated, not archived** (archive `regenerated`): the cut T-Bird, nose-boom and KT-19 files, the
segment fluxes, the placement spread, the window-length experiment, the Polar 6 level per segment, the
gridded values at the segments (`pixi run extract`), `data/model_output/`, and the figures
(`figures_manuscript/output/`).

## 2. Decisions

* **D1, T-Bird 100 Hz (27 October 2026).** The analysis uses the published T-Bird data (995975). The earlier
  input, converted from the ASCII files of the raw-data host, differed from the published version and is
  no longer used.
* **D2, KT-19 and Polar 6 nose boom (27 October 2026).** Both come from the published datasets (995980,
  995974). The radiation file is no longer used (its irradiances are published in 996236).
* **D3, licence of the Zenodo record (27 October 2026).** CC BY 4.0 for the compilation, with the terms of
  each provider stated in the description: ERA5 and CARRA under the Copernicus licence (attribution
  "Contains modified Copernicus Climate Change Service information"), MODIS (NSIDC) and GIBS (NASA) without
  restriction but with citation, the merged sea-ice concentration with the citation and acknowledgement
  the University of Bremen asks for.
* **D4, authors (28 October 2026).** Joshua J. Müller is the creator of the Zenodo record.
* **D5, no new PANGAEA dataset (28 October 2026).** The products derived from the measurements (segment
  fluxes and the rest of C) are not archived separately: the code regenerates them from A and B, and every
  number, table and figure of the paper must be reproducible that way. The leg table, the one input of
  our own that cannot be regenerated without the Polar 6 archive, goes into the Zenodo record.

## 3. Zenodo record

The 22 files are prepared under their record names in `zenodo_upload/` (git-ignored), with
`SHA256SUMS.txt` and `ZENODO_FORM.md` (the text for the form).

1. [zenodo.org](https://zenodo.org) → *New upload*; upload the 22 files. Under *Digital Object Identifier*
   answer "No" and click *Get a DOI now!*: the DOI is reserved before publication.
2. Metadata from `ZENODO_FORM.md`: resource type *Dataset*, title, creator (D4), description with the
   sources and their terms, licence CC BY 4.0, keywords, related identifiers (paper, code repository,
   PANGAEA 995979 and 971763), funding (DFG, TRR 172 (AC)³, project number 268020496).
3. Publish. Files of a published record cannot be replaced; a correction is a new version with its own DOI.
4. Set `RECORD` in `scripts/fetch_zenodo.py` to the record id and check a download into an empty checkout.

## 4. The repository after the Zenodo record

1. `data/` (except `manifest.tsv`), `figures_manuscript/_gibs_cache/` and `figures_manuscript/output/` leave
   git and go into `.gitignore`; `pixi run all` starts with `fetch-pangaea` and `fetch-zenodo`.
   `DATA.md`, `README.md`, `AGENTS.md`, `docs/reproduce.md`, `.zenodo.json` (the code record holds no data)
   and the workflows in `.github/workflows/` (fetch first, then run the chain) are updated.
2. The data are in all earlier commits, including the commits of pull request #1. Rewriting the history
   and force-pushing does not remove them from GitHub: commits referenced by a pull request stay
   reachable. So this repository is renamed and stays private as an archive, and a new public repository
   under the old name receives a history from which the data and figure files are removed
   (`git filter-repo`). The commit messages, which record every change of a printed number, are kept.
3. Code release on Zenodo (GitHub release of the public repository).
4. Paper: the code and data availability section cites the PANGAEA bundle 995979, the master tracks
   971763, the Zenodo data record and the code record.

## 5. Order

1. Zenodo data record: upload, reserve the DOI, publish; set the record id; test a fresh download.
2. Data and figures out of git; workflows fetch; `pixi run all` in an empty checkout.
3. Filtered history, new public repository, code release.
4. DOIs into the paper; final upload copy.
